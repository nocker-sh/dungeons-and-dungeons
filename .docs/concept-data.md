# ゲーム用データと設定資料

## ゲームと `/dev`

`concept/data/` のJSONは、ゲームで使う表示テキスト・画像参照・分類を管理する。`/dev` はその確認用で、裏設定や制作メモは表示しない。

- `characters.json`: キャラ・住民・悪魔。名前、肩書き、職業、ロール、レアリティ、紹介文、装備、立ち絵、アイコン。
- `players.json`: プレイヤーの外見候補。キャラ一覧とは独立し、セリフを持たない。
- `dialogues.json`: 人物のセリフ。`speakerId` で話者を参照し、`scene` と `text` を持つ。人物のページで確認する。
- `world.json`: 背景・モンスターの名前、分類、画像参照。場所の `stands` は店主・案内人が背景のどこにどの大きさで立つか（画面に対する `left`・`bottom`・`height`、縦長 `narrow` と横長 `wide`、並び順は店主・相方）。背景のカウンター・床・扉に合う人の大きさにする。場所の `entrances` は、絵の中の入口へ吹き出しの先端を向ける位置（画像の左上0・右下1、`narrow`・`wide` 別）。街・ギルドのホール・市場で使う。

ゲームの数値・店舗会話・宿会話などは `content/data/` のJSONで管理する。既存の実行用データを資料に複製しない。

キャラの全身立ち絵は `portraits.normal`（通常）と `portraits.skill`（スキル発動）、会話用の上半身立ち絵は `bustPortraits.normal`（通常）、`talk`（会話）、`happy`（喜び）、`sigh`（ため息）、`angry`（怒り）に分ける。`/dev` でも全身と上半身を別セクションで確認する。住民の `portraits` はすべて上半身で、戦闘用アイコンと `skill` は持たない。悪魔の既存の立ち絵は `portraits` に置く。未提供の表情は `null`。ゲームの会話では上半身の通常へ、未提供なら全身の通常へフォールバックし、`/dev` では未提供のスロットを空で表示する。全身の通常・スキル発動は上半身へ置き換えない。

## 裏設定・制作メモ

[[concept/README|設定資料一覧]]から参照する。`.docs/concept/` でキャラ・住民・悪魔・プレイヤー・背景・モンスター・世界観を分類し、1データ1 Markdownファイルで管理する。

各資料のIDは実行用JSONのIDと対応する。構造化した出典・関連・成長方針は正本JSON、背景や制作意図の説明は資料本文に置く。`.docs` をアプリからimportせず、ゲームと `/dev` の配信データに含めない。元モックの記述や仮設定は確定仕様に昇格させない。

## JSONデータベースと文書の対応

構造化した設定データの正本はJSONデータベース [[concept/lore]] に置く。MarkdownのFront Matterには `entity` と正本へのWikiリンクだけを記し、属性を転記しない。共通規約を記す `README.md` は個別資料ではない。名前とIDだけの索引READMEは作らない。

| 項目             | 内容                                                                                                                                                                    |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schema_version` | メタデータ形式の版。現在は `2`。第1版の読み取りも検査で維持する                                                                                                                                          |
| `id`             | 変更しないデータID                                                                                                                                                      |
| `slug`           | ファイル名と同じ識別名                                                                                                                                                  |
| `kind`           | 所属ディレクトリ名。`characters`、`players`、`residents`、`demons`、`backgrounds`、`monsters`、`world`、`weapons`、`armor`、`items`、`materials`、`effects`、`artworks` |
| `title`          | 資料の見出し。ゲーム内の表示名は実行用JSONを正とする                                                                                                                    |
| `runtime`        | `{ file, id }`。`file` はリポジトリルート基準。実行用データがない場合は `null`                                                                                          |
| `related`        | `{ id, document }` の配列。`document` は `.docs` 起点のWikiリンク                                                                                                        |
| `sources`        | `{ reference }` の配列。元モック・ユーザー指示など既知の出典                                                                                                            |
| `gender`         | 任意。人物の性別（`女性`、`男性` など）。未設定なら書かない                                                                                                             |
| `growth_intent`  | 任意。`rate`、`early`、`middle`、`late` に成長バランスの意図を記載                                                                                                      |

関連・出典が未登録なら空配列を使う。正本JSONに置いたID・参照先・出典・成長方針は本文に重複させない。設定の詳しい説明は本文に残す。裏付けのない確定状態や更新日を作らない。

## 画像から確認した造形

武器・防具・道具・素材の資料は `goods.json` と同じIDで対応する。画像参照は `goods-art.json` を正とする。演出画像は `effects.json` と対応する。画像観察のためにゲーム内紹介文・数値・ワザを複製しない。

各個別資料に通常の輪郭・顔・眼・配色・部品・持ち物と、旧案・衣装・動作差分で混ぜてはいけない特徴を記録する。出典・同一性・承認の証拠は[[concept/data/images.json|実行用画像とレビュー状態]]へ保持し、設定本文に画像の一覧を複製しない。人の承認状態を変更せず、観察から生態・能力を確定しない。

独立したJSON項目がない個体差の資料は、devと同じ `<親ID>:<個体slug>` をIDにし、`runtime` は親JSON項目へ対応させ、`related` に親資料を置く。通常・攻撃・睡眠・退場を別個体へ混ぜない。

個別の設定に対応しない挿絵・旧案・アイコンは、非公開の制作記録で管理する。画像の数に合わせて、同じ観察文や一覧だけの設定資料を増やさない。独立した設定がある対象の固有情報は対象の資料へ残し、保管名をゲーム内の確定名に昇格させない。

条件付き会話の台本・表情・出現条件は [[content/data/conversations.json]] を正とする。`/dev/conversations` はプレビューとタイムラインで確認する読み取り専用画面とする。

## 生活と関係を持つ資料（メタデータ第2版）

街・部屋・地図・人・生き物・道具を、背景の一覧ではなく相互に関係する設定として管理する。資料制作では、既存の確定設定を守ったうえで、生活・空間・生態・流通の制作設定を具体化する。新しい制作設定をユーザー承認済みの事実や実装済みの効果とは記録しない。

- `schema_version: 2` とする。第1版の `id`・`slug`・`kind`・`title`・`runtime`・`related`・`sources` は維持する。
- `entity_type` は物理的な対象を表す。`town`、`district`、`building`、`room`、`room-zone`、`scene-template`、`map`、`site`、`person`、`monster`、`good`、`effect`、`visual-record`、`world-system` を使う。ディレクトリによる分類と混同しない。
- `lore_status` は `active`、`supporting`、`archived`、`reference`。不採用の個体や旧画像を現行世界へ戻さない。
- `authorship` は追加設定の出典と適用範囲。`basis` に根拠となる依頼、`scope` に制作設定、`changes_game_rules: false` を記す。既存の確定事項の出典は `sources` を保つ。
- `tags` は検索用。本文の代わりにせず、同じ意味には同じ語を使う。
- `relations` は `{ type, target, meaning }` の配列。対象は資料のIDで参照し、その関係が暮らし・仕事・生態・物語に必要な理由を書く。ファイルへの移動は `related` に持たせる。
- `location` は `{ parent, map, zone }`。場所の親子、地図、建物の階や領域を区別する。部屋を別の建物の部屋としても重複登録しない。
- `bindings` は同じ対象に対応する追加の正本参照。街の背景IDとワールド地図の地点IDのような、見せ方の異なる同一対象を一つの資料へ束ねる。別の街や別の部屋を同一扱いにはしない。
- `runtime` は従来の `{ file, id }` に加え、IDを持たないJSONの根には `{ file, pointer: "" }` を使える。地点のように親ごとに同じIDが使われる対象は `parent_id` を付ける。
- `spatial` は用途、内寸、天井、利用人数、入口、通路、避難、家具と使用範囲。寸法は制作寸法であり、ゲームの回復・価格・定員の規則へ変換しない。
- `life_support` は睡眠、食事、飲み水、洗浄、便所、換気、明かり、保管、出入りと避難の所在。別室を利用するときは資料IDを指定する。「共用設備あり」だけで済ませない。
- `livelihood` は住まい、仕事場、日課、物の調達、収入の行き先。既存の来歴や台詞は正本へ参照し、本文に転記しない。
- `ecology` は生活域、食べ物、隠れ場所、活動、環境中の役目、人の仕事との摩擦。実際の出現とドロップは正本への参照で扱い、新しい能力や報酬を付けない。
- `continuity` は守る設定、採らない解釈、意図的に明かさない事項。未設定の固有名・生死・謎の答えを、資料を埋めるためだけに確定しない。

`kind` には既存の分類に加え、`maps`・`rooms`・`locations`・`sites`・`people` を使う。場面の背景資料は、その場所そのものか、同一空間の寄りか、複数地点で共有する描画ひな形かを `entity_type` で明示する。図が違うだけの同じ部屋を、二つの部屋として数えない。

### 一室一資料と生活の成立

室内資料には、誰が、いつ、何をし、何を持ち込み、どこへ帰るかを記す。寝室は成人の寝る長さ、扉と家具の使用範囲、手元の灯り、換気、荷物、清潔を保つ場所を確保する。仕事室や水回りも、そこで働く人の食事・休息・便所・安全な帰り道まで接続する。炉や薬品のそばを寝床として数えない。

生活機能を別室に頼ること自体はよいが、接続先と運ぶ経路を具体的に示す。人の入れない物入れ・配管の空洞は部屋ではなく設備として扱う。外の道や岩棚は屋外地点として資料化し、屋外に寝台を置いただけで居室扱いにしない。

地図は全体の位置関係、各室はその室の使い方を正とする。通路・階段・出入口は双方の資料から辿れ、扉の先が別の資料では違う場所にならないようにする。ゲームの抽象的な地点間移動と、建物の実際の通路を区別する。

### 資料の検査

`vp run check:concept`で、資料のID、関連先のIDとファイル、実行用JSONの存在とID、地点の親IDを照合する。`coverage.json` は検査する正本と配列の取り出し方だけを持つ。設定本文やゲーム数値の別の正本にはしない。同じ対象の複数のデータIDは `bindings` で束ね、資料の複製で対応しない。 `location.map` は地図資料を参照し、`location.parent` の親子関係は自己参照や複数資料での循環を許さない。共通の地図を複数の場所で参照することは循環ではない。

各層の地図の地点一覧、各地点の `route_to` は実行用の地点と進行先へ照合する。建物の配置図は同階の部屋の重なり、敷地外へのはみ出し、室内の正の寸法を検査する。 配置された対象の `location.map` はその地図を参照し、同じ階へ同じ対象を二度配置しない。階段の同じ区画を上下の階に表す場合は、階ごとに一度ずつ配置できる。L字形の室内は `spatial.footprint` の矩形群で床を表し、外接矩形の欠けた部分を使える床として数えない。 同じ一室の矩形群は和集合として扱い、部分同士の重なりを別室との衝突とは数えない。別室がその床へ入り込む場合は重なりとして検出する。寝室の `spatial.beds` は寝台数、成人が寝る寸法、室外へのはみ出し、寝台同士の重なりを照合する。

一体の動物が共同生活する室内は `animal_support` に `occupant` と、人の `life_support` と同じ生活機能を記す。人の寝台を動物の寝床として流用した扱いにせず、食器・洗浄・排泄・出入りも別途具体化する。

通路は `room-zone` として一つずつ資料を持たせ、寝床数には足さない。廊下の幅や部屋の矩形が通っていても、扉の先へ実際に行けるとは限らない。誰かの寝室や作業中の円を横切らず、各人が食事・洗身・便所・帰還へ移動できるかを本文と図面で確認する。検査成功だけで、避難計画や建築上の安全性、設定の完成を証明したとはしない。

`.docs` はGitで公開するが、アプリ配信の対象にはしない。自動テストは一時ディレクトリの資料で失敗条件を再現し、手元の実資料はこのCLIで別に検査する。資料のないチェックアウトでアプリのテストが資料ファイルを要求する構造にしない。

`life_support` の各機能は `{ target, provision }` を基本とする。共用室から各自の寝室へ戻る場合などは `{ targets: [資料ID, ...], provision }` とし、全員が代表者の私室で眠るような誤った一本化をしない。単一参照と複数参照は併記しない。

建物図の `doors` は戸口を両室で一組にする。階・幅・高さと、両側の `target`・`wall`・`offset_m` を持つ。壁は図の上（yの小さい側）を `north`、下を `south` とし、地理の方位とは独立した図面上の呼称。戸口の開始位置、壁厚相当の間隔、室内側0.9mの余白と寝台の衝突を照合する。L字形は `part` で床の矩形を指定できる。階段の上下と屋外への退避は図面の階と本文も合わせて確認する。

寝台の包含は外接矩形だけでなく、`spatial.footprint` を合わせた実際の床で判定する。床の欠けた部分へ置くことはできないが、壁ではない床の分割線を跨ぐ配置は許す。戸口の `part` は存在する床区画だけを指定でき、戸口の高さは両側の室内の天井高を超えてはならない。

版番号が未設定・未対応の場合や、第2版の `entity_type` が未設定・誤記の場合は検査を失敗させる。未知の版を旧版として扱ったり、対象種別の誤記によって部屋の検査を飛ばしたりしない。不正な資料は、他の資料の参照先や正本の網羅性を満たす資料としても数えない。

`暮らし` タグを持つ人物資料には常住先または条件付き宿泊先を必ず記す。人の `life_support.sleep` と `person` の `resides_in` は、寝台を持つ実際の部屋へつなぐ。通路、作業場、描画ひな形を参照先にしただけでは就寝先にならない。明示した常住者は人物IDごとに一度数え、寝室の利用人数を超えないよう照合する。動物の休む面は `animal_support` で別に扱う。これは明示した常住設定の検査であり、日々の宿泊予約や来客の割当を実装する規則ではない。 `livelihood.lodging` は条件付きの宿泊計画で、`target` を寝台のある部屋へ、`condition` を宿泊の成立条件へ、`routine_section` を本文の移動・収納の説明へつなぐ。常住の `resides_in` と混同せず、空床の割当てと支払いは実行用の規則で判定する。参照先・寝台・条件・一意な見出しを検査する。

生活動線や手入れの文章は本文に一度だけ書く。`livelihood.routine_section`・`handling.routine_section`・`ecology.routine_section` は、その説明を置いたMarkdown見出しの表示上の名前を指す。`##` やリンク先のURLは含めない。同じ資料で見出し名を一意にし、メタデータへ本文を複製する `routine` とは併記しない。参照先がない場合、同名の見出しが複数ある場合、コード例やコメントの中にしか見出しがない場合は検査を失敗させる。

`livelihood.canonical_profile` は会話プロフィールの正本への `{ file, id }` 参照とし、ファイルと一意なIDの存在を検査する。対応するプロフィールがない人物では省略し、人物の正本は既存の `runtime` で参照する。人物IDが別のJSONにあるだけでは、会話プロフィールが存在する根拠にはしない。

## 資料を残す基準

- 本文には現在の仕様、固有の設定、設計の理由、未決定の境界、再現に必要な手順を残す。
- 正本と同じ名簿・ID一覧、日付ごとの修正実況、成功件数、一時ファイルの所在、生成プロンプトを資料化しない。
- 文書への参照はWikiリンクのみ。`.docs` を起点に `[[concept/characters/alma|アルマ]]` のように書き、親ディレクトリ指定やMarkdown形式の相対リンクを使わない。ソースや原画へのリンクはリポジトリ起点のWikiリンクとする。
- 正本JSONの `related.document` もWikiリンクにする。`runtime.file`・`bindings.file`・`coverage.json` の正本参照も、リポジトリ起点のWikiリンクで書く。
- 画像の採用参照は実行用JSONを正とする。一時的な配信パスを個別資料へ転記しない。原画・出典・生成時の指示・承認の証拠は非公開の制作記録へ置く。
