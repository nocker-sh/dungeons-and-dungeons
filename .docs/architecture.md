# 設計とデータの責任

## 目的

仲間を育て、3人で進む・戻るを選ぶ短い判断を積み重ねる。操作ごとに一つの結果を見せ、準備や移動の手間で探索を止めない。確定した遊び方は[[game-spec]]、受入条件は[[features]]を正とする。

## エンジンを独立させる理由

[[lib/wiz]]は不変状態、トランザクション、保存検証を持つ。画面から独立させることで、同じ操作をブラウザ・CLI・試験から実行できる。操作の支払いと拒否条件を画面に複製せず、ユースケースで確定し、Queryで表示する。

ReactはContextから同じエンジンを購読する。ゲーム状態を別のローカル状態へ写さない。乱数・時計・ID・保存先を差し替えられるため、固定条件の再現と本番の動作を同じ規則で確認できる。

基盤はopen-wizのローカル複製を使う。不変状態・保存境界の仕組みを再実装する費用を避け、作品固有の探索・戦闘・街の規則を合成するため。元コミット、原本ハッシュ、ローカルの変更理由は[[lib/wiz/core/provenance.json]]に保持する。端末上の所在は出典に含めない。

## データベースと仕様書

- [[content/data]]は数値・ワザ・入手・会話条件など実行上のルールを所有する。
- [[concept/data]]は名前・紹介・台詞・画像参照など実行時の表示データを所有する。
- [[concept/lore]]は部屋の寸法・生活設備・場所の親子・人物の暮らし・関係・出典・制作案の状態を所有する。
- 設定資料は正本JSONへの `entity` リンクと、固有の意味・設計理由・意図的に未決定の境界を記す。JSONの属性や実行用の台詞・一覧を再記載しない。

設定データは画面上の追加効果を意味しない。部屋の寝台数からゲームの宿泊上限を推定したり、造形案から新しいワザを作ったりしない。制作案と確定仕様、人の承認と自動検査を区別する。

## 変更を安全にする境界

保存は読込境界で形式と参照IDを検証する。拒否された操作は資産・報酬を変えない。読み込めない保存を自動上書きしない。画面の演出時計とゲームの規則は分け、表示途中のHPをエンジンへ書き戻さない。

資料とJSONのID・参照・生活設備・空間配置は `vp run check:concept`、Wikiリンクは `vp run check:docs` で検査する。リンクや寸法の検査だけで、人が生活できる動線や内容の説得力を証明したとは扱わない。検証の選び方は[[verification]]に従う。

## 開発の背景を残す範囲

採用した構造、その理由、制約、未決定事項を残す。実行用の値と操作手順はそれぞれの正本を参照し、日付ごとの実況や古い成功件数を仕様書へ積み上げない。プロンプトは公開可能であり、対象・用途・採用状態を区別して管理する。
